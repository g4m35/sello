# Recurring StockX sale checks

`enqueueStockXStatusChecks` queues at most 25 due, connected production StockX listings each run. Invoke it from the authenticated internal worker before its existing guarded sync-job executor, sharing the worker deadline. It makes no provider calls. `scheduled` means durable work was queued, never that sales were checked. Scheduling failure throws a sanitized 503; the caller must report this failure rather than return healthy counts.

Only `LISTED` listings with an external listing ID and positive unsold inventory are eligible. The existing publication follow-up owns `LISTING` and ambiguous publish outcomes. StockX configuration and listing kill switches must be enabled. Each successful check becomes eligible again after five minutes; oldest unchecked listings are selected first. At most 25 are scheduled per invocation, so a large backlog needs multiple worker runs. The scheduler does not promise a five-minute scan of every listing.

A database transaction locks candidate listing rows with `SKIP LOCKED`. Fresh job reads under the lock exclude pending work even if another scheduler crossed a polling-window boundary. Unique per-listing/window keys prevent duplicate enqueues. All reads and job writes are account-scoped. The connection owner is the job actor; the existing worker verifies current account access and entitlements before any provider request.

Failures, review holds, skipped jobs, and cancellations are not automatically retried as new jobs. Existing bounded worker retries remain authoritative. Explicit admin retry changes the same eligible job back to queued; once it succeeds, recurring monitoring resumes. A newer explicit successful check also permits monitoring after an old terminal failure. Existing review-held work must be resolved through the worker controls; acknowledging a review notification alone does not clear the job. Attempt-exhausted jobs cannot be reset by this scheduler and require investigated recovery. Reconnecting a marketplace alone does not prove the failed operation recovered.

No schema changes, new queue, external credentials, provider requests, or marketplace mutations are introduced by scheduling. The status executor must preserve concurrent sold-state transitions and refresh expired StockX credentials; those fixes are separate integration prerequisites. Tests use a fake transactional database and synthetic listing records, not marketplace calls or production data.
